## 1. 先确认经营规则

下面的问题不要求一次答完。Codex 应先从旧源码、配置和样例记录提取已有规则，列出证据，再让店主确认差异；不要重复询问已经有可靠答案的问题。技术审查与模拟原型可以先做，但影响真实收费、容量、客户归属的未确认项不得以猜测值投入生产。

| 编号 | 需要确认的规则 | 建议的首期处理方式（不是既定事实） | 必须确认的节点 |
|---|---|---|---|
| R01 | 门店所在城市、经营主体、营业时间、休息日；谁使用系统、谁负责后续维护 | 单门店、老板/店员/接送人员三类权限；门店时区独立配置 | 部署及营业排期前 |
| R02 | 猫狗洗护、美容项目；按品种、体重、毛长、打结程度如何收费；是否有起步价和加价 | 简单价目表＋人工调整理由；客人先见参考报价，到店变化需另行确认 | 正式报价前 |
| R03 | 服务实际耗时、可接单员工、工位数量、同一时间可做几只；清洁和休息时间 | 客人提交时间偏好，老板确认；确认时校验实际资源占用，不把“待确认”当已预约成功 | 确认预约前 |
| R04 | 猫狗寄养房/笼位数量、规格、隔离要求；同一家多宠能否同住 | 先按真实、可独立占用的笼位建档；共住未确认时不自动合并占位 | 接受寄养预订前 |
| R05 | 寄养按自然日、晚数还是满 24 小时计费；入住/退房时点、晚退、节假日、提前离店、清洁缓冲 | 采用一套经店主确认的简单计费规则，保留报价明细；占位区间和计费区间分别计算 | 寄养报价及上线前 |
| R06 | 接受寄养/洗护的疫苗、驱虫、年龄、健康和行为条件；紧急联系人、异常处理和送医授权 | 只记录声明、查验状态及店主处理决定；未知不当作已合格；不自动诊断或生成用药方案 | 接宠前 |
| R07 | 接送范围、单程/往返收费、按趟还是按宠物收费、时间段、等待/爽约费用；谁执行、一次能带几只 | 人工报价、人工派单；往返拆为两个行程；首期不自动算路线和距离价格 | 确认接送前 |
| R08 | 是否收预约预付款；取消、改期、爽约、部分取消、寄养延住的规则 | 未确认之前不自动收费或自动扣罚；订单标注待处理；已经确认的免费取消规则可以自动执行 | 开启相关动作前 |
| R09 | 当前会员类别、已有储值余额、赠送余额、折扣；扣款顺序、可用服务、退充值规则 | 基础会员＋储值流水；本金与赠送余额分开。未确认赠送规则则不启用新赠送；已有赠送余额不得丢弃 | 余额迁移和启用扣款前 |
| R10 | 现金、微信、支付宝、银行卡、平台团购等实际收款方式；能否混合支付、部分付款、赊欠；谁能退款 | 首期核实到账后登记；退款/改价/余额调整由老板授权并留痕；不以截图自动认定到账 | 财务功能试营业前 |
| R11 | 老客档案如何认领；家庭共用电话如何处理；是否愿意接入短信验证；旧手机号是否仍有效 | 首期手机号验证登录＋店主核验旧档案归属；无法验证时只允许提交新的预约申请，不开放历史和余额 | 客人历史查询开放前 |
| R12 | 服务照片和寄养记录给谁看；是否做复购提醒、提醒间隔、退订方式 | 对客记录和内部备注分开；先做老板待办和手动分享；营销通知单独取得意愿，不自动群发 | 分享记录及提醒前 |
| R13 | 微信小程序、公众号、商户号、美团/抖音门店及应用是否已有；各自实际获得哪些能力 | 逐项核查实际账号、主体、类目和权限，不把“有商家账号”当成“有开发接口” | 对应集成阶段 |
| R14 | 旧源码和数据库备份的准确位置；哪些是真实客户/余额，哪些是演示数据；是否存在未完订单 | 只读盘点、脱敏试迁移、店主核对；不把测试账户或未知余额直接导入营业环境 | 正式迁移前 |
| R15 | 域名、部署地区、运行预算、短信/照片成本、运维负责人；可接受丢失多久的新数据、恢复多久 | 单套轻量服务；账本恢复能力为上线条件；成本清单确认后才购买资源 | 公网上线前 |

### 1.1 待确认项怎样进入开发

用 `docs/business-rules.md` 维护 `编号、问题、已有证据、建议、店主决定、确认人、确认日期、影响模块`。决定状态只用 `待确认 / 已确认 / 暂不支持`，不要写含糊的“基本确定”。收费、取消、排期等规则要有版本；订单保存下单时适用的版本，不能被后续修改追溯改变。

未确认容量时，可以开发并演示“申请—人工确认”的界面，但真实环境不得展示保证可订的库存。未确认储值规则时，相关入口关闭，不能以默认零余额代替迁移。未取得外部权限时，保留真实可用的人工流程，不以假接口响应伪装成功。

## 2. 已明确的边界与成功标准

### 2.1 已知事实与尚未验证的内容

按项目负责人提供的信息：旧程序是 Electron＋SQLite，已有可恢复的 JavaScript 源码及完整备份；新仓库位于 `E:\Pet-store`，当前为 `main` 分支、只有 README、工作区干净；E 盘原始备份保留。后续源码、规划和测试在新仓库维护。

本次网页版审查调用本地 Review 时返回连接 404，未读到 E 盘旧源码和数据库。因此，上述本地状态仍需 Codex 实测，旧代码可复用比例、表结构、数据完整性和历史余额均没有得到本次独立验证。本规划不基于假想的旧表名或实现。

### 2.2 产品目标

主线是“减少录入、减少追问、减少排期冲突、减少对账错误”，不是复制旧桌面软件的所有页面。客人能登记与提出预约，老板能快速确认，员工能完成任务，服务与资金都能追溯。

首期只做单店。不建设连锁组织、商户入驻、多租户计费、复杂积分商城、自动调度平台、库存采购 ERP、自动薪酬或 AI 客服。旧 Electron 不作为首期客户端，不建设桌面 SQLite 与云数据库的双向同步。

### 2.3 使用体验验收目标

以下为待试用验证的目标，不是已经达到的成绩：老客再次预约应复用已有宠物和服务信息，仅确认变化；店主从今天工作台直接确认、派单、开始服务和查看待结账；寄养照护记录以实际勾选和可选照片为主，不能为了省事默认所有宠物“正常”；价格、退款、扣余额等重要动作允许多一次确认，不能以减少点击为理由省略核对。

## 3. 首期最小可用版本：做什么，不做什么

“首期 V1”指阶段 1～3 逐步完成后的完整营业版本。阶段 1 是内部试用切片，不应把尚无寄养、接送和客人端的阶段 1 宣称为全部需求已交付。

| 模块 | V1 必做 | 后期可选或明确不做 |
|---|---|---|
| 客户与多宠物 | 一位客户多只宠物、联系方式、必要照护提示、历史记录、检索及受控合并 | 家庭多账号共同管理、跨店档案 |
| 洗护美容 | 项目和参考价、报价确认、预约/临时到店开单、每只宠物的服务进度 | 复杂动态定价、自动美容师匹配 |
| 寄养 | 按真实笼位查空位、预订、入住、每日记录、延住冲突检查、退房与结算 | 多宠共笼自动分配、复杂季节收益管理 |
| 上门接送 | 单程/往返、地址联系人、时间窗口、费用、派单、交接和异常状态 | 自动路线规划、实时定位、拼车优化 |
| 会员与资金 | 基础会员、核验过的储值余额、本金/赠送区分、充值/消费/退款流水、组合收款、日结 | 在线自助充值、积分、复杂套餐/次卡（除非现有业务必须处理） |
| 客人网页 | 扫码登记、申请预约、取消/改期申请、自己的服务记录、再次预约 | 复杂商城和社交功能 |
| 信息沟通 | 后台待办、对客状态页、手动复制通知、经授权分享照片与记录 | 未授权自动微信推送、自动读取私人聊天 |
| 复购 | 可选的建议复约日期、老板待办、客人再次预约入口 | 默认固定周期群发、强制营销授权 |
| 支付/平台 | 人工核实到账、平台来源与核销记录、待结算及差异登记 | 未获权限的支付下单、自动核销、自动抓取平台账单 |
| 运维与安全 | 权限、审计、自动备份及恢复验证、脱敏测试、导出、错误提示 | 把安全和资金一致性延期到 V2 |

若门店当前根本不经营储值，可以关闭充值入口，但保留经设计和测试的开关与流水结构；若已经有储值或次卡，必须先确认迁移和消费方案，不能为了缩小 V1 而损害客户既有权益。

## 4. 页面与操作流程

### 4.1 老板和员工端：手机优先，电脑展开

| 导航入口 | 页面内容 | 高频动作 |
|---|---|---|
| 今天 | 待确认预约、待到店、服务中、待接送、今日入住/退房、待照护、待收款、异常 | 确认、开始、完成、安排执行人、联系客人 |
| 排期 | 日/周服务安排、员工占用；寄养空位与入住表；接送时间表 | 查冲突、改期、延住、查看执行人员 |
| 客户 | 搜索客户、多宠物档案、服务与寄养历史、必要提醒、会员余额 | 老客再开单、补充宠物、核验档案归属 |
| 收银 | 应收明细、组合付款、充值、退款、待核实、日结及渠道差异 | 确认到账、结算、核对、导出 |
| 更多 | 项目价格、笼位和人员、规则、账户权限、备份状态 | 少量低频配置 |

订单详情尽量在一页呈现客户、每只宠物、服务、寄养、接送和账单，避免反复进入不同管理页面补填同一信息。复杂内容折叠，首页不堆经营分析图表。

### 4.2 客人端

页面为“门店与服务、登记/我的宠物、预约、我的订单、订单/照护详情、我的资料与会员”。预约表按选择逐步展开：不选接送就不要求地址，不选寄养就不展示入住须知，不为了登记一只宠物要求填完整档案。

新客填写本人必要联系方式、宠物称呼及猫/狗、服务和期望时间；报价依赖体重等信息时才补充对应字段。估价必须注明不是最终确认价；信息不够时显示“需店主确认”，不能以 0 元代替未知费用。

客人端不得展示内部风险讨论、其他客户信息、员工私密资料或未经允许的照片。

### 4.3 接送执行人端

不单独开发一个司机 App。在同一个响应式管理网页中，按权限提供“我的接送任务”：当前授权范围内的行程、方向、宠物数量及注意事项、时间窗口、必要地址联系人、一键拨号/复制地址、交接/异常按钮。司机不能看客户储值、完整消费史、全店账单。

### 4.4 核心流程

**洗护美容：** 扫码登记/选择老宠物 → 选择服务和期望时间 → 需要时申请接送 → 提交待确认 → 老板确认价格与资源 → 到店交接 → 服务中 → 完成并发布必要记录 → 核实收款/扣余额 → 店内交还或送回 → 订单结束。

**寄养：** 选择起止时间和宠物 → 提交申请 → 检查适配笼位及照护条件 → 确认预订和报价 → 入住核验与交接 → 每日实际照护记录 → 延住重新查空位、确认差价 → 退房检查 → 费用结算与交还 → 完成清洁后释放实际可用状态。

**接送：** 选择单程/往返 → 记录各段地址、联系人、时间窗口、费用 → 老板安排执行人 → 接宠交接 → 到店交接；需要返程时另有“店内接出 → 送达主人”任务。两个方向允许不同日期、人员、地址和状态。

**收款：** 从已有订单自动带出应收 → 分配储值和其他渠道金额 → 对人工渠道核实到账后确认 → 原子写入收款与消费流水 → 显示剩余应收或待退款。客人提供的付款截图只可作为待核实材料。

**再次预约：** 从已完成服务选择“再次预约” → 复用宠物和服务 → 按现行规则重新估价、选择新时间 → 提交新的申请。不得直接复制旧价格、旧容量占用或旧健康查验状态。

### 4.5 失败与断网

所有保存提供成功/失败反馈，失败后保留非敏感输入或允许重新操作，不显示假成功。V1 不做离线扣余额、离线自动收款和双向同步。服务不能因网络故障被迫中断：现场可纸质记录并电话联系，恢复后由授权人员补录，分别保留业务发生时间与补录时间，并检查重复。

## 5. 技术路线：独立后台，模块化单体

### 5.1 推荐栈及复核条件

| 层 | 推荐 | 约束 |
|---|---|---|
| 网页 | Vue 3＋TypeScript＋Vite，响应式布局 | 老板与客人使用不同路由和权限；手机不是把电脑大表格缩小 |
| 后台 | Node.js LTS＋NestJS＋TypeScript | REST API；业务逻辑放服务端模块；不依赖 Electron IPC |
| 接口契约 | OpenAPI＋可生成的客户端类型 | 字段、错误、认证、分页、状态转换和幂等要求写清楚 |
| 数据库 | PostgreSQL；Prisma 可作为默认数据访问工具候选 | 交易、约束、迁移与真实数据库集成测试不可省；必要的原生 SQL 随迁移管理 |
| 工作区 | npm workspaces＋单一锁文件 | 不同时引入多套包管理器；初期不需要 Nx/Turbo |
| 部署 | Linux 上单套 API＋网页＋PostgreSQL，HTTPS 反向代理 | 单店模块化单体；不引入微服务、Kubernetes、常驻消息队列集群 |
| 图片 | 本地开发用受保护目录，生产用私有对象存储或有等价权限与备份的私有存储 | 数据库存元数据，禁止把营业图片/数据库提交 Git |
| 测试 | 单元测试＋真实 PostgreSQL 集成测试＋浏览器端到端测试 | 工具在依赖兼容性核查后选定一套；手机微信内置浏览器须真机验收 |

本次查询 Node.js 官方发布页显示 24.x 为 LTS，建议初始化时选择仍受支持的 24.x 最新补丁并锁定；正式安装前再复核依赖兼容性，不盲目追随 Current 版本。[S01] NestJS 提供 OpenAPI 文档支持，可用于契约产出。[S02]

这是一条推荐路线，不要求为换框架而重写已有可用业务。如果阶段 0 发现旧程序已把稳定、可测试的服务逻辑清晰分离，优先提取复用；若 Codex 建议改用其他轻量后端，应写一份简短架构决定，说明维护者熟悉度、迁移成本和测试策略，再确认。不要同时开发两个后端。

### 5.2 结构

```text
老板/员工响应式网页 ─┐
客人手机网页 ────────┼─ HTTPS /api/v1 ── 同一业务后台 ── PostgreSQL
后续微信小程序 ──────┘                       │
                                    私有照片与附件
                                            │
                           按需增加支付/通知/平台适配器
```

后台按客户宠物、服务订单、预约资源、寄养照护、接送、会员资金、身份权限划分模块，但仍是一个部署单元。首期没有必要建设通用工作流引擎、营销规则引擎或独立财务微服务。

网页和小程序共用的是接口、服务端业务规则、数据库、客户和订单编号、资金流水、资源校验、权限及审计。客户端只做展示、输入帮助和交互；最终价格、可用余额、可预约性和可见数据必须由后台决定。

### 5.3 未来小程序哪些保留，哪些重做

| 内容 | 后续处理 |
|---|---|
| 后台订单、寄养、接送、资金等业务模块 | 继续使用，不建设另一套数据库或另一个“微信业务后端” |
| OpenAPI 契约、状态枚举、纯数据校验规则 | 在运行环境允许的前提下复用，客户端校验不替代服务端校验 |
| 客人预约、我的宠物、订单、照护记录、会员页面 | 默认按需要重做小程序界面，重新测试导航、表单、上传、分享和生命周期 |
| 登录、网络请求、文件上传、支付拉起、消息授权 | 实现小程序端适配；微信身份由服务器交换和绑定 |
| 老板管理网页 | 可继续保留，不因客人端有小程序而强制重写 |
| 老 Electron 页面与 IPC、本地文件和本地 SQLite 访问 | 不是直接可用的小程序页面；按功能提取业务，不搬运桌面依赖 |

Vue 官方把网页、桌面以及面向不同宿主环境的使用方式分别列出；它不是承诺网页界面无适配地变成微信小程序的机制。[S03] 本项目明确不承诺一键转换。若后续采用 uni-app 等多端工具，也必须以实际页面适配和真机验收为准；不为潜在复用率牺牲首期的可用性。

## 6. 身份、权限与数据安全

### 6.1 客户档案不等于登录账号

`customer_id` 是门店业务档案；`user_id` 是系统登录主体；微信、短信等是登录身份。门店可以先建立客户档案，之后再由客户认领，二者不得机械合一。

推荐 H5 客人使用手机号验证码登录，但短信通道需要实际开通。没开通之前，新客仍可填写并提交新的预约申请；当前浏览器的受限会话只管理本次新申请，不凭填入的手机号查出老客历史或余额。“免验证码输入手机号即显示全部档案”禁止上线。

通过短信验证只能证明当时控制该号码；涉及导入的老档案、共用号码、号码变更、合并账户或已有余额，应结合店内核验处理归属。不要根据相同姓名或手机号自动合并所有记录。

无短信时，老客自助历史查询的替代流程是店主核验后发放用途受限、短时、可撤销的一次性绑定凭证；实现并通过安全验收之前，只提供新预约申请和人工沟通，不伪装成完整账号功能。不要用可转发的永久订单 URL 作为完整账户凭证。

后续微信身份按 `provider＋appid＋subject` 保存映射，使用自己稳定的 `user_id/customer_id`；不把 OpenID 当通用客户主键，也不假定不同微信应用身份自然相同。实际登录与手机号能力在接入阶段按官方账号权限复核。

### 6.2 后台强制的最小权限

老板可配置价格和资源、批准退款和余额调整、导出和日结；店员只处理获授权的订单及照护工作；接送人员只看被分配任务所需信息；客人只看被授权的本人档案和订单。多人兼岗可组合权限，但不能靠共用老板账号实现。

每个读写请求、图片访问和导出都校验身份、角色、对象归属及当前状态。隐藏按钮不是权限控制；随机 ID 也不是授权。此设计对应 OWASP 的最小权限、逐请求授权和对象/静态资源保护建议。[S04]

### 6.3 上线前最低安全要求

默认拒绝未授权访问；密码安全哈希；登录限速；短信验证码有效期、尝试次数及发送频率限制；生产环境禁用演示登录与 Mock 支付。H5 登录采用安全会话 Cookie 等成熟方案并防 CSRF；小程序使用适配其环境的登录凭证，后台仍使用同一授权服务。不要将密钥、数据库凭据和支付签名材料放到客户端。

照片按对象权限访问，不使用公开可枚举路径。服务端校验实际文件类型、大小、像素和数量，移除不必要的定位元数据；首期不接受 HTML/SVG 等可执行或复杂内容。客户内容按文本安全渲染，导出表格对公式注入进行转义。

只收集实现预约、服务和接送所需的信息。接送地址、联系方式和照片设置用途、访问范围和保留规则；公开营销照片另行取得许可。隐私告知、账户解绑、更正/删除申请和记录保留冲突的处理方式应在上线前确定；账务需要保留的信息采用受控留存或去标识方式，不以一个“删除账号”按钮直接清空账本。所在地适用的法规、储值经营要求和必要备案，须依据真实主体和地区另行核查，本稿不作已合规判断。

## 7. 业务状态与联动规则

### 7.1 不要用一个 status 管全部业务

| 对象 | 建议主要状态 | 重要边界 |
|---|---|---|
| 预约申请 | 待确认、已确认、已拒绝、已取消、爽约 | 待确认不承诺资源；爽约由规则或人员核实，不随意扣费 |
| 服务任务（按宠物） | 已安排、已到店、服务中、已完成、已交还、中断 | 付清不等于服务完成；一只完成不代表全单完成 |
| 寄养 | 已预订、已入住、待退房、已退房、已取消/未入住 | 延住是受校验的动作；实际超时未退房继续显示占用与冲突 |
| 每段接送 | 待安排、已安排、前往交接、已接宠、已送达、异常、已取消 | “送达”按该段目的地解释；取送两个方向独立 |
| 收款记录 | 待核实/处理中、成功、失败或作废 | 人工登记与 API 回调具有不同的确认依据 |
| 退款记录 | 已申请、处理中、成功、失败 | 退款成功前不能宣称钱已退回 |
| 订单财务 | 未付、部分付、已付、待退款、部分退款、已退款等派生状态 | 尽量由应收调整、收款分配和退款结果计算，不允许随意改标记 |

每次转换记录操作者、时间、前后状态与必要原因。允许店主经授权处理异常，不允许通用接口随意覆盖任意状态。

### 7.2 必须实现的跨模块联动

确认预约时，在同一事务中验证最终规则、写资源占用和确认状态；并发确认冲突时只允许可满足条件的申请成功。多宠申请默认整体确认；若允许部分确认，必须让客户明确看到哪只宠物已确认，不能后台静默拆散。

改期/延住时，先验证新时间和差价，在事务内替换或增加占用；不能先释放旧占用后再尝试抢新资源。失败则旧安排保持不变。

取消订单应检查已发生的服务、照护和行程；释放未开始部分的预留资源，取消尚未执行的关联任务，保留已完成记录，并按规则生成应收调整及必要退款申请。宠物已经在途中或店内时，转为异常/交还处理，不因订单取消自动中断照护。

服务超时、寄养晚退、接送延迟会影响后续安排，必须显示待处理冲突；不要到计划结束时间便自动宣称物理资源已经空闲。已批准但无法按时履约的新预约要联系调整，不通过把已存在预约从数据库隐藏来“解决”冲突。

若美容师同时执行接送，接送计划占用也必须进入该人员排期。首期只做合理的时间窗口和人工预留，不假装知道路况，不自动承诺精确到分钟的到达时刻。

## 8. 核心数据结构（逻辑设计）

下表是领域对象，不要求阶段 0 一次创建全部表。物理表在旧数据审查与规则确认后按阶段落地；名称可调整，但关键关系不能丢失。

| 数据组 | 建议对象/表 | 核心字段或关系 |
|---|---|---|
| 门店配置 | `store_settings`、人员可用时间 | 时区、营业日、规则版本、能力开关；仅一店，不扩成租户平台 |
| 登录权限 | `users`、`auth_identities` | 角色/能力、账号状态、身份提供方、应用标识、身份 subject、绑定信息 |
| 客户 | `customers`、客户与账号绑定 | 联系方式、来源、会员类别、档案归属核验；手机号不当主键 |
| 宠物与地址 | `pets`、`customer_addresses` | 所属客户、称呼、种类、报价所需属性、必要照护信息；地址按需收集 |
| 服务目录 | `services`、价格/规则版本 | 项目名、服务种类、适用宠物、价格与时长配置、有效期 |
| 订单及报价 | `orders`、`order_items`、报价版本/应收调整 | 客户、来源、状态；明细关联宠物、数量、单价、优惠、报价理由及确认记录 |
| 预约与洗护 | `booking_requests`、`service_visits` | 期望时段、确认时段、服务宠物、人员、业务状态、关联订单 |
| 资源占用 | `resources`、`resource_reservations` | 真实员工/工位/笼位、适用条件、占用起止、占用类型、关联任务、有效状态 |
| 寄养 | `boarding_stays`、`boarding_care_logs` | 宠物、订单、预订/实际入住退房、笼位安排、照护日期与内容、作者、对客可见性 |
| 接送 | `transport_requests`、`transport_legs`、行程宠物关联 | 订单、单程/往返；各段方向、地址快照、联系人、时间窗口、报价、执行人、交接状态 |
| 收款 | `payment_receipts`、`payment_allocations` | 付款渠道、金额、核实方式、外部参考、确认人；分配到订单或充值的用途 |
| 退款 | `refunds`、退款分配记录 | 对应原收款/原储值消费、金额、原因、状态、审批及执行依据 |
| 会员储值 | `wallet_accounts`、`wallet_entries` | 本金与赠送分桶；有符号金额变动、来源业务、操作者、原交易/冲正关联 |
| 平台与日结 | `external_order_refs`、`daily_closings`、核对记录 | 平台及外部编号、人工/接口来源、核销证据、应结算/实到账/手续费、差异与处理 |
| 文件及追踪 | `media_assets`、`audit_events` | 对象所属、存储 key、类型与校验、可见范围；重要操作的前后变化 |
| 迁移与幂等 | `import_batches`、旧新 ID 映射、`idempotency_keys` | 导入批次/源记录/目标记录；请求主体、动作、key、载荷摘要、结果 |

### 8.1 关系要求

一位客户拥有多只宠物；一张订单允许包含多只宠物的不同服务明细。洗护任务和寄养记录按宠物独立，不把宠物名拼成一个文本字段。首期每只宠物一个主要归属客户，其他联系人只作业务联系人；多人共同账户权限待后期明确再扩展。

寄养占用与计费明细分离，同一只宠物换笼位可有多段资源记录，但不能产生无故重叠或断档。占位要包含约定的清洁缓冲；实际资源可用性还需检查真实在店状态。

一次往返接送至少有两条可独立执行的 `transport_legs`，可关联同一订单多只宠物。地址与价格保存任务快照，客户后来修改地址簿或价目表，不得修改已经确认的历史任务。

一张订单可以有多笔收款、部分付款和部分退款。充值是一笔资金到账及储值增加，不是虚构的洗护服务订单；订单取消、减项或退款需有应收调整依据，不能只在订单上写负数抵消所有历史。

### 8.2 通用字段与约束

主键采用稳定内部 ID；业务单号单独生成。金额以整数分保存，币种明确；输入校验合理上限，避免浮点误差及超出整数安全范围。时间戳统一存可明确时区的时间，界面及寄养计费按门店时区；若确认门店在中国大陆，可设 `Asia/Shanghai`，不要使用开发者电脑的时区推算晚数。

重要业务对象具有创建、修改时间和并发版本；明细保存成交快照。联系方式、证据及日志避免无控制的无限保存。已入账流水和关键历史禁止普通编辑/删除，用可审计的反向记录或调整处理错误。

### 8.3 防超订不能只靠页面提示

首期优先用明确的真实资源占用表达容量，例如一个笼位在某时间区间只允许一个有效占用。采用 `[开始, 结束)` 区间并另行包含清洁缓冲，可避免相邻时段边界解释混乱。

PostgreSQL 的范围类型及排斥约束支持表达同一资源的区间不重叠，可作为笼位/明确工位预留的数据库保障。[S05] ORM 未直接支持时，在版本化迁移中管理原生 SQL 及扩展依赖，不能以省事为由撤掉约束。对需要多个资源或复杂数量的安排，另配合事务、资源行锁/一致的锁顺序、失败回滚和有界重试；不能把一条区间约束当成已解决所有容量问题。

## 9. 资金规则：首期就做对，不等在线支付再补

### 9.1 三件事分别记录

界面分别展示服务应收/已结算金额、外部实际收付、会员储值变动。不要把充值和之后的储值消费重复累计成“今天收到的钱”。这些是店内管理口径，不替代正式会计、税务或法定预付资金报表。

例如，仅用于测试：同一天客户实际充值 500 元，再用余额消费 120 元，且无赠送及其他交易，则外部收款为 500 元、储值消费为 120 元、余额为 380 元。不能显示外部收款 620 元。

本金和赠送金额分别记账；扣款优先级、折扣适用及退充值处理由 R09 确认。没有规则时不擅自启用“充 500 送 50”。旧系统已有赠送余额而无法区分时，列为待核验，不任意算成可退本金。

### 9.2 不可省略的资金约束

余额变动、订单支付分配、收款确认以及相关状态更新放在同一数据库事务中。余额账户并发锁定或使用具有同等效果的一致性方案，余额不足时整体失败；不能前端检查一次余额后直接减。账本为事实依据，缓存余额只可作为可校验的派生值。

每个收款、充值、扣款、退款和导入动作都必须有持久幂等保护。按钮禁用只是交互帮助，不是防重机制。同一主体、动作和幂等 key 重试且请求一致时返回相同结果；同 key 不同内容返回冲突，不偷偷创建第二笔交易。幂等记录与业务唯一约束一起设计，避免过期后又重复入账。

退款必须追溯原始资金来源，限制原支付剩余可退额度，并同时考虑处理中退款的预占额度，防止两个并发退款各自通过。储值消费退款回对应储值分桶；外部支付退款按原方式或经明确授权的异常流程处理，不能把赠送余额变成现金。组合付款允许分次退款，但每个分配和审批理由都可追踪。

原应收已确认后发生减项、取消或补价，生成调整明细和客户确认记录。退款会改变原收款净额，业务应收也需要对应的减少依据；不以“删掉原订单”代替。无法联系客户、资金渠道未确认或原记录缺失时，转待处理，不擅自执行。

### 9.3 人工收款与平台券的首期处理

人工收款记录 `渠道、金额、发生时间、核实人、核实时间、可用的外部参考`。输入“客户说已付”或上传截图只能进入待核实；老板查看实际商户收款记录后才确认。退款同样在实际完成后确认，不能点击申请即标为成功。

美团/抖音券在官方商家端核销后，登记平台、券/订单参考号、核销人员与时间及服务对应关系；系统状态清楚标注“人工核验”，不是“接口已验证”。同一外部凭证禁止重复抵扣。券面金额、门店应结算金额、平台手续费和真正到账金额分别记录；未知金额用待确认，不用 0 冒充已经核实。

平台券抵扣可以结清客人的对应服务应付部分，但不代表平台已经把钱打到店里。日结应能单列平台待结算、到账和差异。

### 9.4 后续在线支付追加的要求

接入后采用后端下单、验签/解密通知、主动查单、幂等更新及定期对账；核对商户、应用、业务单号、币种和金额。官方文档明确小程序前端回调不是最终可靠的支付判断依据；以服务端查询及支付通知核实结果。[S06][S07]

同时覆盖延迟通知、重复通知、通知先后顺序变化、关闭页面、请求超时但实际支付成功、取消订单与付款同时发生等情形。业务已取消也不能丢弃后来到账的真实资金，应进入受控退款/异常处理；在未查清支付状态前，不生成可能导致重复收费的新动作。

## 10. 共享 API 契约

采用 `/api/v1`，明确公开、本人和员工三个访问范围。可以分别使用 `/public`、`/me`、`/staff` 路由，但内部调用同一业务服务，不复制三套订单规则。以下是需求级接口，最终路径可以调整，语义必须保留。

| 能力 | 示意接口 | 约束 |
|---|---|---|
| 公共门店与服务 | `GET /public/store`、`GET /public/services` | 只提供可公开数据；价格性质说明明确 |
| 日期/时段查询 | `GET /public/availability` | 仅参考或当前快照，不因查到可用就保证预订成功；不泄露人员隐私 |
| 登录与身份 | `POST /auth/sms/request`、`POST /auth/sms/verify` | 真实通道开关、限速；不泄露手机号是否对应会员余额 |
| 客户和宠物 | `GET /me/pets`、`POST /me/pets` | 所有权由已验证身份决定，不能由请求任意指定别人的 customer_id |
| 申请预约 | `POST /booking-requests` | 支持受限新客申请；幂等；服务、宠物、寄养和接送信息按规则验证 |
| 确认/改期/取消 | `POST /staff/booking-requests/{id}/confirm`；对应动作端点 | 确认占用在事务内；客户端取消与员工处理权限分开 |
| 本人订单和记录 | `GET /me/orders`、`GET /me/orders/{id}` | 数据脱敏；不返回内部备注、非本人宠物或财务后台字段 |
| 报价及最终应收 | 订单下的报价、确认和调整端点 | 服务器计算金额；人工改价也需要理由与权限 |
| 寄养 | 预订、入住、照护记录、延住和退房动作端点 | 每宠物记录；延住检查新资源及费用；对客可见性明确 |
| 接送 | 申请、派单、每段状态更新端点 | 实际任务权限；往返独立；地址快照；改派留痕 |
| 资金 | 收款确认、储值消费、充值、退款申请/确认端点 | 事务＋幂等＋资金来源关联；客人端不得自行确认到账 |
| 对账和导出 | 日结、渠道核对、受控导出端点 | 按权限，留审计；导出不含不必要敏感字段 |
| 图片 | 授权上传/完成确认、授权读取端点 | 服务端验证文件及对象归属；签名读取凭证短期有效 |

成功响应具有稳定的资源标识与版本；错误响应至少包含机器可识别代码、面向用户的信息和可追踪 request_id。定义 `RESOURCE_CONFLICT`、`INSUFFICIENT_BALANCE`、`PRICE_CHANGED`、`STATE_CONFLICT` 等业务错误，不把所有错误都显示成“服务器异常”。

关键写操作支持 `Idempotency-Key`；并发编辑采用 `expectedVersion` 或等价机制。服务端拒绝客户端传入的越权字段和未知状态值。列表有分页，日期金额格式统一，错误码、认证方式与幂等语义写入 OpenAPI。

API 测试应能不经任何页面完成一次完整业务流程，这也是后续小程序可复用后台的验收证据。未来新增客户端不复制数据库，不导入服务端 ORM 实体到客户端，也不让客户端直接连 PostgreSQL。

## 11. 阶段任务与完成条件

### 阶段 0：旧程序审查、规则确认表与最小原型

**目标：** 知道可以复用什么、必须确认什么，以及阿姨能否理解新的流程。

Codex 先核实仓库根目录、分支、远端和工作区，不执行清理或覆盖。查找项目内已有的源码/备份说明；未知的 E 盘备份路径由负责人给出，不递归扫描整块磁盘猜文件。只读审查可用源码、依赖、旧 SQLite 表结构和记录性质；原始数据不进入版本控制。检查旧业务是否和 Electron IPC、文件操作及 SQL 强耦合。

交付 `legacy-audit.md`、`business-rules.md`、`architecture.md`、`migration-plan.md` 和阶段任务表。先做今天工作台、单页订单、客人预约、寄养表、接送任务的低保真原型；原型可以用明确标注的虚构数据，不应借机搭建全部后台。

**验收：** 每个复用结论有实际文件/函数证据；缺失内容明确列出；既有余额与演示数据的区分办法明确；店主能走通 5 个核心操作；原始备份无改动。没有数据库或无法打开时报告限制，不写“迁移通过”。

### 阶段 1：老板内部可用的洗护、订单、会员及账本

**前置：** 技术路线批准；必要报价、资金、权限规则确认；测试与营业数据隔离。

搭建工作区、配置、API、PostgreSQL 迁移、登录权限、今天工作台。完成客户多宠物、服务价目、人工预约/临时到店、资源确认、每宠物服务状态、应收明细、人工到账登记、会员储值、组合收款、退款、日结和审计。先按“开单—服务—结算”完整纵向流程交付，不先铺满十几个空页面。

旧资料先脱敏试迁移；需要营业试用时，仅导入经过批准和核对的真实数据。已存在储值的客户，未核清余额不能启用其自动扣款。

**验收：** 阿姨可用手机独立完成老客开单、收款和查询；重复点击与并发扣款不重复记账；退款与原款可追溯；手机和电脑看到同一份最新业务数据；后台恢复演练可还原账本。缺陷未通过前不扩大到所有业务。

### 阶段 2：补齐寄养与接送

**前置：** 真实笼位、寄养计费、接宠条件、接送规则已确认。

完成寄养空位、预订入住、照护记录、照片可见性、延住校验、晚退冲突、退房和清洁可用状态。完成单程/往返、独立行程、多人派单、交接、异常及取消联动；接送占用与员工服务排期兼容。

**验收：** 两人同时抢最后一个笼位不会超订；延住撞到后续预订明确失败或进入人工调整而非直接覆盖；往返两段不同执行人可分别完成；司机无法读取余额；取消不抹掉已完成照护及行程。

### 阶段 3：客人扫码网页与受控试营业，形成 V1

**前置：** 公网域名和 HTTPS；客人身份验证路径、隐私告知、必要备案与主体要求已核查；数据权限与备份已通过验收。

完成手机扫码登记、宠物档案、预约申请、本人订单和照护记录、取消/改期、再次预约、会员只读查询、复制通知与客户可见记录。首次新客登记不强迫填写无关信息；老客账号认领按规则核验。二维码仅带门店/渠道信息，不包含客户手机号、家庭地址和密钥。

先选择少量真实客户试用，观察阿姨是否仍需重复录入，修复流程阻塞后逐步推广。若短信尚未开通，只能进行清楚标注能力范围的“新申请版”试用，不能将历史查询等未可用功能宣称为完整 V1 已验收。

**验收：** 在手机微信内置浏览器以及门店电脑走通登记—申请—确认—履约—结算—再次预约；客人只能访问自己的数据；待确认清楚可见；照片权限有效；下单、收费、容量与身份的关键用例全通过。

### 阶段 4：客人微信小程序（后期）

先核查实际主体、类目、AppID、备案/审核状态、服务器域名、隐私声明、身份与消息能力，再决定具体客户端方案。重做或适配客人页面、登录、上传、网络、分享和生命周期。老板管理端继续用网页即可。

**验收：** 网页和小程序读写同一客户、订单、余额及寄养资源；在一端创建的数据另一端可见；没有独立于后台的微信计价规则；跨端身份绑定不会误认领；正式审核及真机验证通过。此阶段即使没有在线支付，也可继续人工到账登记。

### 阶段 5：在线支付与适度通知（可按需求与阶段 4 调序）

实际商户能力具备后，只接入当下必要的一种支付场景，完成下单、通知、查单、退款、对账、超时与关单。检查当前小程序交易类运营要求；官方小程序支付开发指引提示，交易类小程序还需按适用规范处理订单发货管理等要求，不应把“能调起支付”当全部完成。[S08]

通知按实际有权使用的通道与模板实现，可退订、可记录失败、可由老板查看待发送任务；不承诺普通 H5 或小程序能无限推送微信消息。

**验收：** 真实授权环境中的成功/失败/取消/重复通知/部分退款/账单差异等用例通过；每笔资金可与渠道核对；旧人工流程仍可处理缺失能力与故障。

### 阶段 6：美团/抖音等平台及增长工具（可选）

按实际交易量和重复录入成本决定是否值得接入，先实现一项确有权限且能节省工作的能力。分别核实开发者身份、应用资质、商家授权、具体接口范围和费用。抖音官方接入资料区分自研商家与服务商，并说明接口权限和商家授权要求；不能直接套用另一类开发者的流程。[S09][S10] 美团也应选择与门店服务相匹配的服务零售业务能力入口，不以餐饮/外卖接口代替。[S11]

继续保留人工核销登记、官方导出文件的受控导入、平台待结算台账。禁止未经授权抓取、模拟登录、复制私人登录 Cookie 或冒充官方核销结果。

根据门店实际复购节奏评估提醒、会员优惠和次卡。接送量明显增加后再比较人工安排与路线优化收益；先积累经授权的必要订单数据，不提前采集实时位置。

**验收：** 在真实获批范围内完成接口测试、去重、退款/核销状态及账单核对；权限撤回或接口失败后有可用替代流程，不拖垮主业务。

### 12.1 自动化与人工验收分工

单元测试覆盖计费、折扣、状态转换、退款分配、日期边界和输入校验。数据库集成测试使用真正的 PostgreSQL，验证事务、范围约束、唯一性、并发扣款和并发退款，不以 SQLite 测试替代 PostgreSQL 行为。

端到端测试覆盖四条关键流程：洗护结算、寄养延住、往返接送、客人预约。人工验收重点是阿姨的真实操作、手机拍照/上传、微信内置浏览器、联系人拨号与异常沟通。测试报告记录实际命令、环境、结果和未覆盖项；没有执行的测试必须标“未执行”，不能称全通过。

试营业统计登记耗时、老客重复录入次数、待确认遗漏、照护漏记、资金差异和冲突处理情况。先记录基线，再比较改善，不编造“节约 80% 时间”之类成果。具体性能阈值在服务器与试用规模确定后制定，不能依据页面打开一次就宣称可承载高并发。

## 13. 旧 Electron＋SQLite 的复用与迁移

### 13.1 先审查，后决定复用

业务词汇、价目数据、字段含义、稳定的纯 JavaScript 计算函数和有效样式资源可能复用；应为原逻辑添加特征测试后再移植。Electron 窗口、IPC、桌面文件读写、本地 SQL、只适合电脑录入的页面流程需要隔离或替换。不得未经审查运行不明旧安装包或把旧依赖整体搬入新公网系统。

旧 SQLite 是迁移来源，不成为多人使用时由多个客户端直接打开的共享文件。原始备份保持只读，后续处理仅使用批准的工作副本。

### 13.2 数据盘点与一致性快照

确认真实源库、附件目录、可能的 WAL 文件和最后使用时间。源程序仍在运行时，应使用能取得一致性快照的方法；SQLite 官方 Online Backup API 提供运行中数据库一致备份机制，不能把任意时刻复制一个正在写入的 `.db` 文件当成可靠备份。[S12]

记录源文件校验值、快照时间、表结构、行数和异常，但不要把原始电话号码、地址、资金明细贴入公开文档或提交 Git。原始存档及可能关联文件不要遗漏或擅自清理。

### 13.3 迁移次序与核对

```text
只读盘点 → 一致性工作快照 → 字段映射 → 脱敏试迁移 → 异常与余额核对
→ 店主批准 → 确定切换时点/暂停旧端写入 → 最终快照 → 正式导入 → 复核
```

优先级是实际客户与宠物、有效会员余额、未完成订单/寄养/接送，其次为历史服务记录。是否只迁移活跃数据、历史数据留只读档案，由店主决定。不要为追求全量迁移耽误使用，也不能私自丢弃仍影响权益的记录。

每一源记录保留 `legacy_source＋legacy_id` 映射，幂等导入。异常去向可追踪，包括重复联系方式、宠物无客户、未知价格规则、日期格式问题、真实/演示身份不清和余额不一致。

储值若有可靠明细，校验其重建结果；若只有经过确认的期初余额，使用明确标识的开账流水，保留来源与核验人，不伪造历史充值。无法核实的账户暂缓启用；每个账户与总余额都核对，不只核对记录数。

### 13.4 切换与回退

在最终迁移时约定旧系统停止写入的时点，记录迁移批次并保留旧程序只读查询。上线后不要两套同时记账。应用回滚必须兼顾数据库迁移版本；新系统已经产生真实交易后，不可简单恢复旧备份而抹掉新交易，应先导出并核对增量，按回退预案处理。

## 14. 部署、外部依赖及替代流程

### 14.1 外部依赖清单

| 依赖 | 什么时候必须具备 | 无权限/未准备好时的替代 | 上线核查材料 |
|---|---|---|---|
| 域名、服务器、HTTPS | 公网客人 H5 前 | 本地/隔离测试，不把开发隧道或个人电脑当生产服务 | 所有人、预算、运维账户、证书、监控与恢复办法 |
| 地区/主体及适用备案、隐私与储值经营要求 | 对应公开运营或资金业务前 | 暂不公开或关闭有关能力；不声称已满足 | 实际主体、部署地区、经营地区及确认记录 |
| 短信验证 | 推荐 H5 账号完整功能前 | 新预约受限会话；店主核验后的一次性绑定（经测试） | 通道、签名/模板、费用、发送限额和失败处理 |
| 微信小程序主体、类目与域名配置 | 小程序阶段 | 继续使用 H5，共用原后台 | 实际账号可用能力、审核状态、隐私配置、测试记录 |
| 商户支付产品 | 在线支付前 | 真实到账人工登记＋受控退款登记 | 商户主体、产品权限、密钥保管、回调与对账测试 |
| 微信或其他通知能力 | 自动通知前 | 后台待办＋手动复制通知＋客人主动查看记录 | 可用模板、授权方式、额度/价格、失败重试和退订 |
| 美团能力 | 自动核销/同步前 | 官方商家端操作＋人工记录/受控文件导入 | 具体业务入口、接口权限、店铺授权、撤权处理 |
| 抖音生活服务能力 | 自动核销/同步前 | 官方商家端操作＋人工记录/受控文件导入 | 自研/服务商身份、接口权限、店铺授权、验收 |
| 地图/定位服务 | 距离计价或自动导航功能前 | 地址文字、复制地址、电话沟通；不用经纬度也能派单 | 接口与使用限制、费用、精度、隐私需要 |
| 私有图片存储与备份目的地 | 营业照片与真实数据上线前 | 可选择受保护自有存储，但必须满足权限与恢复验收 | 访问策略、数据保留、成本上限、恢复测试 |

平台资料会变动，且不同主体能看到的能力不同。公开文档存在不等于该店已获准使用。本次未验证实际微信/美团/抖音账号，微信开发者站部分具体页面无法直接读取，因此手机号、订阅消息、登录配置及类目等具体权限与费用，不在本稿中作确定承诺；由集成阶段在真实账号与当时官方文档中复核。

### 14.2 运行维护底线

开发、测试、生产数据和密钥隔离；生产数据库不直接暴露公网；服务自动重启，日志脱敏且轮转，监测数据库空间、证书、进程、错误率和备份失败。预算先列类别再采购：服务器/数据库、域名、照片存储与流量、短信、支付/平台相关费用、备份和维护工时，不未经核查给固定价格。

首期可采用一台合适的 Linux 服务器部署网页、API 和数据库，备份存到独立受控位置；是否改用托管数据库由维护者能力和实际报价决定。不要自动复用其他项目的服务器、账号或数据库。

**建议恢复目标，须批准并实测：** 新增账务最多丢失 1 小时，故障后 4 小时内恢复主要业务。小数据量可采用定期一致性数据库备份及独立图片备份，较高要求再评估更细粒度恢复；具体频率和方式应确实覆盖目标，不能仅靠每日一次备份宣称符合 1 小时目标。恢复报告记录实际恢复点、耗时、余额核对和附件可用性，达不到就调整或如实标注。

备份加密、权限隔离、保留期限明确；保管恢复所需密钥并测试可用性。迁移和破坏性结构调整前单独备份。不能用“备份文件已生成”替代“已从备份恢复验证”。

### 15.2 每个开发切片的交付要求

每次只推进一个已批准、可验收的完整流程，先说明依赖和规则，再实现数据库/API/界面/测试，最后交付可重现的演示及结果。必要文件同步更新，改了规则要改测试。

每次汇报包含：完成范围、改动文件、数据库迁移、实际测试命令与结果、未完成与阻塞项、启动方式、下一步。没有测试证据就写未测试；演示数据不能冒充真实商户联调；取得 HTTP 200 不等于业务验收通过。

锁文件提交；依赖安装先核对现有环境，不强制重装无关 Python、Codex 或系统组件。数据库变更以受控迁移执行，禁止把临时 schema push 当生产迁移方案；特殊数据库约束要有回归测试。

不得擅自删除或改写 E 盘原始备份，不运行 `git reset --hard`、无审查的 `git clean` 或全盘清理，不覆盖用户未提交改动。对仓库提交和推送遵循用户当次授权；默认不自动推送、不购买服务、不发布生产、不操作真实支付、不发送真实营销通知。
