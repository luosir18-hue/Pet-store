# 架构决定 · Phase 0

状态：本轮建议落实为后续实施基线；没有初始化真实业务后台或数据库。用户已授权开始本轮改造。

## 审阅结论及调整

采用原规划的 Vue 3 + TypeScript / Node.js LTS + NestJS / PostgreSQL / REST + OpenAPI 路线。旧实现有独立 store 文件，但 SQL、文件系统和业务高度耦合，缺失新业务模型；适合复用字段含义和少量纯函数，不适合直接开放旧 IPC。

原规划无需推翻，实施时明确四点：

1. 阶段 1 拆成可验收的开单—服务—结算切片，而非先建所有模块空壳；寄养、接送、客人端完成后才称 V1。
2. 界面中的服务完成与交还进一步拆开。数据库用独立 custody/handover 记录宠物持有方；寄养已退房不意味着已送达主人，返程送达也不意味着款已付清。
3. “确认最终价/资源”与“接受预约申请”分开。未知价格为 null/待报价；未定义生产规则的能力关闭，不把测试默认值部署成门店政策。
4. 小程序先留后台契约和身份映射，页面后期适配。真实商户准入随相关阶段核实，不阻塞本地原型，不伪造成功回调。

## 本机环境与依赖决定

实际 Windows PowerShell，Git 可用，Node v24.15.0、npm 11.12.1；psql 和 docker 未在当前 PATH 找到（不等于机器绝对未安装）。没有使用其他项目数据库，也没有安装/启动 PostgreSQL。

阶段0采用原生 HTML/CSS/ES modules 和 Node 内置静态服务器，无 npm 依赖；不是更换正式 Vue/Nest 技术路线。正式工程阶段1建立 npm workspaces 和一份锁文件，锁定已验证的具体版本。Prisma 是候选，安装前验证 Node/PostgreSQL 兼容性和原生范围约束的迁移支持；本轮未验证整套依赖兼容性。

2026-09-14 复核 [Node 发布页](https://nodejs.org/en/about/previous-releases)：24.x 为 LTS，本机补丁不是该网页所列最新补丁。当前本地原型可运行；正式部署另选届时受支持且已测试的补丁，不改全机 Node。

## 单套后台

```text
老板/员工网页 ─┐
客人 H5 ──────┼─ /api/v1 ─ 唯一 NestJS 应用 ─ PostgreSQL
未来小程序 ───┘             ├─ 私有媒体存储
                            └─ 支付/通知/平台适配器（按阶段）
```

模块：身份授权、客宠档案、服务目录/报价、订单/履约、预约资源、寄养照护、接送交接、资金账本、日结/审计。模块服务互相调用，业务写操作由一个事务编排器完成；首期不引入微服务和消息集群。

Vue 适合响应式组件化网页；采用它不保证微信页面自动复用。[Vue 宿主环境说明](https://vuejs.org/guide/extras/ways-of-using-vue.html)

Nest 提供生成 OpenAPI 规范的模块；后端 DTO 与动作契约生成规范，随后生成调用类型。客户端不导入 Prisma 实体，不包含计价权威实现。[Nest 官方 OpenAPI](https://docs.nestjs.com/openapi/introduction)

## 状态、事务与契约

| 动作 | 服务端原子边界 | 冲突/失败 |
|---|---|---|
| 确认预约 | 检查报价/规则版本 → 按固定顺序锁资源 → 写占用 → 确认申请 | RESOURCE_CONFLICT，原申请仍待确认 |
| 改期/延住 | 检查当前版本及新范围 → 校验差价 → 替换占用并保存报价快照 | 失败全部回滚，旧入住不变 |
| 收款/充值/消费 | 幂等键及载荷摘要 → 锁钱包/订单 → 有效金额校验 → 分配/流水/状态/审计 | INSUFFICIENT_BALANCE、IDEMPOTENCY_CONFLICT；不留半笔 |
| 申请退款 | 锁原支付分配 → 计算已退及处理中预占 → 记申请及占额度 | 不超退；外部退款处理不占长事务 |
| 确认退款结果 | 验证来源与金额 → 幂等写反向流水/分配 → 完成状态 | 申请成功不等于真实退款成功 |
| 取消/改派 | 锁订单任务 → 判断实际持有方 → 取消未开始占用/任务 → 审计 | 已接宠进入异常交还；旧司机后续访问失效 |

每个动作有 Idempotency-Key、expectedVersion、request_id。相同键相同载荷返回原结果，不同载荷冲突；关联业务唯一键防幂等记录到期后重复。金额 integer/bigint 分，API 金额格式一致且检查安全范围；禁止客户端任意传入成功状态。

身份用户 user_id 与客户 customer_id 分开；未来微信映射 provider + appid + subject。老板、员工、接送人员按授权范围；客人按已验证绑定。图片/导出同样检查对象权限。H5 会话与 CSRF、小程序令牌适配共用同一授权服务。

单笼位等明确资源使用 `tstzrange` + 排斥约束表达不重叠，单独包含清洁缓冲；实际仍在店时不得只因计划到期认定空闲。多个资源/人员并发仍需事务和有序锁。[PostgreSQL 范围类型及排斥约束](https://www.postgresql.org/docs/current/rangetypes.html)

部署目标 Linux 单应用＋数据库＋HTTPS，生产密钥和私有存储在代码外。完整备份包含数据库和媒体，恢复点/耗时由预算与实测确认。本轮只运行绑定127.0.0.1的原型白名单服务器，不能对外营业。
